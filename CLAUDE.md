# Пиксириус

Песочница «падающего песка» на canvas: клеточная симуляция материалов, жидкостей и газов с теплом, ветром, химией и жителями. Чистый JS в браузере, без сборки, без зависимостей и без npm.

## Запуск и проверка

- Запуск: `node tools/serve.js` → http://localhost:8080 (или конфигурация `pixilius` в `.claude/launch.json`). Сервер отдаёт файлы с `Cache-Control: no-store` и заголовками COOP/COEP: без них у страницы нет `SharedArrayBuffer`, и симуляция идёт в одном потоке. `?threads=N` в адресе задаёт число рабочих потоков, `?threads=0` — один поток; сколько их сейчас, видно в подписи скорости времени (вкладка «Разное»).
- Публикация: репозиторий github.com/ruslexco-commits/pixirius, игра — GitHub Pages (https://ruslexco-commits.github.io/pixirius/, ветка main, корень; `.nojekyll` — без обработки Jekyll). Pages не шлёт COOP/COEP: их добавляет сервис-воркер `coi-sw.js`, который index.html ставит, только если страница не изолирована (локально не ставится). Все пути в страницах — относительные: сайт живёт в подпапке /pixirius/. Диагностика (`diagReport`) шлётся только с localhost (`DIAG_ON`).
- `diag.log` в корне — диагностика страницы через `tools/serve.js` (POST `/__diag`): зависания главного потока дольше 3 с с этапом кадра (`pixDiag` в main.js, сторож — фоновый рабочий поток), их длительность, ошибки страницы и рабочих потоков. Ошибка в кадре цикл больше не останавливает — показывается внизу экрана. Жалуются на зависание — сначала прочитать этот файл.
- `node tools/check.js` — самопроверка без браузера: согласованность таблицы элементов, полнота `swapFields`, прогон сцены (исключения, NaN, мусорные типы, состав долей), отмена и сохранение побайтно, быстрые пути против прямого расчёта (пропуск пересчёта устойчивости, `windHypot`), замер мс на `step()` при 576x324.
- `node tools/mechanics.js` — прицельные проверки механик: маленькая сцена под одно правило и утверждение о результате (падение замёрзших жидкостей, отмена ветра, плавление окислов и остатка, ржавчина по стадиям, обрушение балки). При намеренной смене правила правится и проверка.
- `node tools/threads-check.js [рабочих]` — многопоточный обход в Node (`worker_threads`, тот же код и общая память): общая фаза (ветер, тепло, выходы луж) по потокам побитно как в одном потоке, мир цел (тип сходится с составом, нет NaN), массовые виды вещества не расходятся с однопоточным прогоном, замер ускорения. Побайтно с одним потоком мир не совпадает и не должен (см. шапку `js/sim/threads.js`).
- `node tools/lockstep-check.js [кадров]` — мир по сиду (мультиплеер): две копии с одним сидом и одними действиями идут побайтно одинаково, в том числе копия, снятая посреди прогона (`lockstepDump`/`lockstepLoad`), и мир с рабочими потоками против одного главного (`updateBands`). Падает — значит, в снимок не попало что-то, от чего зависит ход, или шаг зависит от чего-то вне мира (время, `Math.random` мимо `withRng`).
- `node tools/wire-check.js [кадров]` — провод мультиплеера (`js/mp-wire.js`): двоичный формат возвращает то же (Map, Set, typed-массивы, общие ссылки, -0/NaN), мир размером с игровое поле через упаковку, сжатие, нарезку и сборку идёт побайтно как оригинал, порядок сообщений за асинхронно сжимаемым миром сохраняется, чужой адресат не распаковывает. Печатает размеры мира: сырой и по проводу. Новый вид значения в сообщениях или мире — сначала сюда.
- `node tools/neural.js [--full]` — опыт: нейросеть (клеточный автомат 3×3) вместо `sim.step()`. Вывод записан в шапке файла: как замена шага не годится (вещество не сохраняется, медленнее на CPU). Повторять его, только если меняется сама идея.
- `node tools/compare.js [ref] [шагов]` — побайтное сравнение поведения рабочей копии с коммитом (по умолчанию `HEAD`): одно и то же зерно `Math.random`, одна и та же сцена. **После рефакторинга обязан выдать OK.** При намеренной смене поведения он показывает, с какого шага и в каких полях началось расхождение.
- Стенд (`tools/harness.js`) грузит все скрипты из массива `files` в `index.html` до `js/render.js`. Сцена и воздействия заданы в `buildScene`/`poke`. Новую механику стоит добавить в сцену, чтобы `compare`/`check` её покрывали.
- Изменение, заметное глазу (рендер, UI, ввод), проверяй ещё и в браузере.
- Поле рисует видеокарта (`js/render-gl.js`). `?cpu` в адресе включает прежний путь на CPU (`Renderer.cellColor`): он же служит запасным, если WebGL2 нет или контекст потерян. `renderer.gpuDiff()` в консоли сверяет GPU с CPU на текущем кадре: норма — `maxDelta` 0 или 1.

**Методы Sim разложены по файлам.** В каждом `js/sim/*.js`, кроме core, объявлен класс-контейнер (`class SimHuman { ... }`), а в конце стоит `extendSim(SimHuman)`: она переносит методы в `Sim.prototype`. Внутри это обычные методы Sim с обычным `this`. Если одно имя метода объявлено в двух файлах, `extendSim` бросает ошибку. Новый метод клади в файл своей подсистемы, новую подсистему выноси в новый файл по тому же образцу.

### Кадр (`Sim.step`)

`computeStability` (пропускается, если скелет не изменился, см. `structureChanged`) → `updateBeams` → `updateLanding` (приземлившиеся тела давят на пятно контакта; только в кадр, где пересчитывалась устойчивость) → `updateWind` → `updateTemp` (при потоках вместо них и `computeLiquidEscape` — одна фаза `globalPassesParallel`: ветер, выходы луж и строки тепла одновременно на разных потоках, побитно так же) → снимок ветра на кадр (`snapshotWindFrame` → `windVXFrame`) → общий бросок `_windRoll` → `computeLiquidEscape` → `updateSleep` (какие куски 16x16 обходить) → `computeDebrisWindChance` → обход клеток **снизу вверх**, с чередованием направления строки по чётности кадра, спящие куски пропускаются. При запущенных потоках обход идёт вертикальными полосами по 32 столбца в две фазы (`updateParallel`), а люди, колонисты и подрывы откладываются и досчитываются главным потоком в конце (`processDeferred`). Для каждой клетки: `react()` (реакция по типу), затем движение по категории (`updatePowder`/`updateLiquid`/`updateGas`/огонь; осыпавшееся твёрдое с `stability===0` падает как сыпучее). `moved[i]=1` помечает клетку, которая в этом кадре уже ходила.

### Состояние клетки

Всё хранится в typed-массивах длиной `w*h` с индексом `i = y*w + x`. Поля, которые переживают кадр, перечислены в `PARTICLE_FIELDS` (core.js): `type, life, extra, shade, temp, moisture, sol, sol2, stain, dirt, fall, crushed, beam, beamExtra, colonistHomeX/Y`. Отмена, сохранение и `clear()` работают строго по этому списку.

`life` и `extra` у каждого элемента означают своё:

| элемент | life | extra |
|---|---|---|
| FIRE | кадров до угасания | 1 = от дерева (оставит золу) |
| SMOKE | кадров жизни | — |
| OILFILM | — | направление единственной связи (0↑ 1→ 2↓ 3←) |
| OXIDE*, METAL_OXIDE*, EARTH_OXIDE | — | стадия окисла (см. `oxideStage`) |
| ACID_RESIDUE | — | уровень 1..4 (с 5 — реагент) |
| HUMAN | личный номер → память в `_humans` | 1 = мёртв |
| PROTAGONIST | номер игрока мультиплеера (0 — одиночная игра), состояние — `players[номер]` | 1 = мёртв |
| COLONIST | единиц груза | материал груза |
| CLONE | — | запомненный элемент |
| LAMP | кадров свечения после жёлтого заряда (LAMP_CYCLE) | — |
| EARTH / WET_EARTH | счётчик кадров тика влажности | — |
| газ VAPOR с маслом | срок до выпадения масла | — |

Прочее:
- `sol` + `sol2` — **состав клетки, он есть у каждой непустой клетки**: 10 долей, доля — элемент в своей фазе (вода, пар, лёд, камень...), до 5 разных веществ; пустота не хранится (10 минус сумма). Читать одним числом — `sim.comp(i)`, разбирать — `solGet/solSlot/solMatter`. Тип клетки выводит из состава `setComposition()`: одни газы — газ (один вид — его элемент, несколько — `VAPOR`); иначе твёрдых (и сыпучих) долей не меньше жидких — твёрдое по преобладающему, поровну — тоже твёрдое; иначе жидкость (смесь растворов — `SOLUTION`). Газ в одной клетке с другим выходит отдельным пикселем (`splitGas`). Кипение/замерзание — превращение долей по `PHASE_LINKS`. Цвет — среднее цветов долей (`solColor`), пустота — прозрачность. У твёрдого состав меняется только извне (растворитель, окисление); у `hasComposition`-типов он живёт сам (`tickComposition`). **Меняя тип клетки в обход `spawn`/`setComposition`, поменяй и состав** (пример — `retypeComp` в `setOxideStage`): `check.js` сверяет тип с составом у каждой клетки.
- Сплав (`ALLOY`) и расплав (`MOLTEN_ALLOY`) — тип по составу, как у раствора: `setComposition` ставит их для смеси двух и больше сплавных долей (металл, сталь, медь, камень, их ржавчины) или расплавов. Их свойства по типу не читаются — только по долям через методы `sim/alloys.js` (устойчивость, стойкость, ток, кислота, плавление, масса); новое место, где свойство берётся по id, для сплава надо так же развести. Металлы, камень и их ржавчины плавятся по долям (`reactMelt` → `meltAlloy`), так что примеси переживают плавку.
- `beam` — второй слой, балка: id её материала (0 — балки нет), `beamExtra` — стадия окисла материала. Материал — клетка, с которой начали вести (`pickBeamMaterial`); от него балка берёт цвет, устойчивость и стойкость (`stabId` отдаёт материал), плавление и реакции с жидкостью в своей клетке (`reactLiquidOnBeam`). Ставится только в пустоту, жидкость и газ. Её нет в `type`: жидкости, газы, сыпучее и люди проходят сквозь неё. Держит только твёрдое. Сохранения до версии 2 хранили здесь маску опор — при загрузке такие балки становятся каменными. Сама держится по устойчивости, как камень: балка с `stability === 0` в том же кадре становится камнем (`updateBeams`), и весь неподдержанный пролёт осыпается разом.
- `temp` принадлежит частице и едет вместе с ней. `spawn()` прибавляет к температуре места собственную температуру элемента (`baseTemp`/`DEFAULT_BASE_TEMP`), но не дальше неё: место, уже не холоднее (у льда — не теплее), остаётся как есть, и повторный спавн тепло не копит. Источники тепла ставят `heatSource`.
- `stain` — пятно крови (0..255) на клетках вокруг раздавленного падающим твёрдым (`crushBody`), едет с частицей; цвет подмешивают `Renderer.cellColor` и шейдер. У живых (человек, протагонист) это отравление реагентом или окислом камня (`poisonTick`, sim/human.js): растёт, пока касается яда, иначе спадает; рисуется жёлтым, на 255 — рассыпается сыпучим окислом.
- `dirt` — у живых это урон от ударов протагониста (`hitCreature`, sim/human.js: +HIT_DAMAGE за удар, три — смерть с кровью вокруг, заживает), рисуется красным; у прочих — грязь на пикселе (`MUD_DIRT_PER_PART` за долю): мутная вода откладывает её на твёрдое и сыпучее, вода забирает обратно, грязь сохраняется (sim/mud.js); едет с частицей, цвет — к цвету грязи (`Renderer.cellColor` и шейдер, текстура `uDirt` — шестнадцатая, больше WebGL2 не обещает).
- `fall` — клетка падает в составе осыпавшегося тела (ставит ветка обломков в `updateCell`); по нему `updateLanding` находит тело, вставшее на опору. `crushed` — сколько кадров клетка ещё продавлена (0 — нет, отсчёт `tickCrushed` в `updateLanding`). Продавленная опору дальше передаёт как обычно, но сама стоит с устойчивостью 0 (`zeroCrushedStability` в конце `computeStability`; бит в подписи `structureChanged`) и осыпается, если есть куда. Сам пиксель не меняется. Счётчик живых продавленных `_crushLive` пересчитывает `wakeAll` (отмена, загрузка, очистка).
- Заряды (`sim.charges`, sim/charges.js) — не клетки, а сущности поверх поля: номер, клетка, путь, срок, данные. В отмену и сохранение не входят (`restore`/`deserialize`/`clear` их гасят). Проводимость — таблица `CHARGE_STEP` по id; новый проводник вписывается туда.
- Ветер (`windVX/VY`) — грубая сетка `airCell=4`. Входит в снимок отмены (`snapshot`: иначе отмена падения оставляла поток от несуществующего тела), но не в файл сохранения.

## Чек-листы

**Новый элемент**
1. `EL.X` в `data/elements.js`: следующий свободный id, строго < 64, иначе сломаются таблицы по id.
2. Запись в `ELEMENTS` (`id, name, cat, color, density, flammable` и нужные опции: `maxStability/toughness`, `meltPoint/meltChance/meltsInto`, `boilPoint`, `dispersion`, `heatSource`, `baseTemp`, `acidImmune/acidSlow`, `burnChance/burnLife`).
3. Если он нужен в палитре — в `ELEMENT_ORDER`. Если это техника — ещё и в `TECH_ELEMENTS`.
4. Предикаты по смыслу: `isStructural`, `isAnchor`, `isAirtight`, `isHeatInsulator`, семейства долей в `data/composition.js`, реакции людей `humanDeadly`/`humanDanger`. Фаза доли берётся из `cat`; если у вещества есть газ/твёрдая форма — строка в `PHASE_LINKS`. Растворитель берёт всё с фазой, кроме исключений `DISSOLVER_MIXABLE`. Предикаты устроены как таблицы по id (`IS_STRUCTURAL = idTable([...])`): элемент вписывается в список таблицы.
5. Своё поведение: метод в файле подсистемы плюс `case` в `Sim.react()` (core.js). Начальные `life/extra` — в `spawn()`.
6. Если цвет зависит от состояния, а не только от `ELEMENTS[id].color`, — `Renderer.cellColor` **и** шейдер в `js/render-gl.js` (поле, от которого зависит цвет, — ещё и текстурой в `GpuCellPainter`). Затем `renderer.gpuDiff()` в браузере.
7. Если у элемента особое поведение (реакция, газ при растворении, коррозия), описать его в справке лупы (`js/inspect.js`): правила словами там повторяют код.
8. Добавить в сцену `tools/harness.js`, затем `node tools/check.js`.

**Новое поле клетки**
1. Завести typed-массив в конструкторе Sim.
2. Вписать его в `PARTICLE_FIELDS`, указав `empty` и `moves`.
3. Если `moves: true` — добавить обмен в `swapFields` вручную: это горячий путь, цикл по списку там дорог. `check.js` падает, если его забыли.
4. Поле появится и в отмене, и в сохранении само. Старые файлы без него получат `empty`.
5. Если поле читают или пишут при обходе клеток — вписать его в `THREAD_SHARED_FIELDS` (threads.js), иначе рабочие потоки увидят свою пустую копию.
6. Если поле начинает читать `computeStability` — добавить его в подпись `structureChanged` (stability.js). Иначе пересчёт устойчивости будет пропускаться, когда меняется только это поле; `check.js` ловит это, только если его прицельные правки задевают поле.
7. Если это не мир, а управление вкладки (как `paused`, `timeScale`, состояние кисти), — вписать в `LOCKSTEP_SKIP` (lockstep.js): иначе мультиплеер перешлёт его вкладкам вместе с миром. Всё остальное на `Sim` уходит в снимок мира само.

**Новая подсистема или механика**: новый `js/sim/<имя>.js` по образцу существующих, вписать в `files` в `index.html` после `core.js`, константы настройки держать в начале файла с комментарием.

## Правила кода

- Комментарии на русском, и объясняют они **почему**, включая историю: какой баг был, какая просьба пользователя за этим стоит. Так уже написан весь код, и новое пишется так же. Устаревший комментарий правится вместе с кодом.
- Тонкие места, на которых уже ломались, записаны в комментариях рядом. Перед правкой прочитай комментарий у функции.
- **Производительность**: обход клеток — это ~187 тыс. клеток на кадр. В коде, который вызывается на каждую клетку:
  - никаких выделений памяти (массивов, объектов, замыканий);
  - никаких `Map`, чтений объекта `ELEMENTS[id].x` и вызовов цепочек функций там, где хватает плоской таблицы по id (примеры — `IS_STRUCTURAL`, `IS_MOVABLE_ID`, `DENSITY`, `HEAT_WEIGHT`, `OXIDE_FRAIL_FROM`, `LIQUID_PHASE`);
  - дорогое делается не каждый кадр, а по броску вероятности или с периодом (`RUST_TICK_CHANCE`, `HUMAN_SCAN_PERIOD`);
  - полный проход по полю, результат которого часто не меняется, пропускается по точному признаку: пересчёт устойчивости при неизменном скелете (`structureChanged`), строки тепла, холодные вместе с соседями (`markHotRows`), строки ветра, нулевые вместе с соседями (`diffuseWind`), толчок ветром в штиль (`_windPushQuiet`), пересчёт устойчивости, пока меняются только обломки без опоры (`stabChangeHarmless`), поиск кусков, которые пора будить по теплу (пометки `_chunkHeatWake` ставит сам проход тепла), слой балок словами по 4 клетки (`updateBeams`);
  - клетка, которой заведомо нечего делать, выходит сразу, если по пути не тратится `Math.random()`: пустота мимо `updateCell`, глубина лужи и зажатый с боков песок (`updateLiquid`/`updatePowder`), чистая полная клетка в `tickComposition`, несостоявшееся ржавление без `setComposition`.

  Оптимизация не должна менять поведение: `node tools/compare.js` обязан выдать OK. Отсюда два запрета. Нельзя убирать или переставлять вызовы `Math.random()`: сдвинется вся последовательность. Нельзя заменять формулу на «почти такую же» (например, `Math.hypot` на `Math.sqrt(a*a+b*b)`: последний бит расходится, и мир идёт иначе; см. `windHypot`). Замер — последняя строка `node tools/check.js`.
- Движение частицы — только через `swap()` (обмен плюс возмущение ветра) или `swapFields()`, когда одно логическое движение складывается из цепочки обменов. После хода ставь `moved[цель] = 1`. Руками поля не копировать: так уже терялись температура и состав.
- `spawn()` создаёт свежую частицу (сброс `extra`/`life`, чистый состав своего элемента, своя температура). Чтобы сменить тип, сохранив частицу (температуру и оттенок), ставят `type` напрямую, как делают `setComposition`/`setOxideStage`.
- **Сон** (sleep.js): кусок, где ничего не менялось `SLEEP_AFTER` кадров, не обходится. Изменение замечается через `markDirty(i)`: его уже зовут `spawn`, `clearCell`, `setComp`, `swapFields`, `setComposition`, `setOxideStage`. **Любая другая прямая запись в поля клетки (`type`, `life`, `extra`, `moisture`, `beam`...) обязана позвать `markDirty(i)`**, иначе кусок уснёт с незаконченным делом. Клетки, которым нужен ход каждый кадр при неизменном поле (огонь, горячее, растворы у твёрдого...), перечислены в `restlessCell`: новая механика такого рода дописывается туда.
- **Потоки** (threads.js): клетка при обходе может трогать соседей только в пределах своей полосы плюс `THREAD_REACH` (12) столбцов. Дальний горизонтальный поиск ограничивать `_colMin/_colMax` (как путь вытеснения жидкости и `shiftChain`), вертикальный свободен. Дело шире этого (заливка, взрыв) или использующее `Map`/объекты главного потока откладывать: `if (this._inBand) { this.defer(...); return; }` (как `detonateGunpowder`, `detonateSalt`, люди). Потоки включаются, когда бодрствующих кусков много (`THREAD_MIN_ACTIVE`) или однопоточный обход дольше `THREAD_SERIAL_MAX_MS` (куски, набитые движущимся веществом). После правки обхода — `node tools/threads-check.js`. В мультиплеере на время игры (`sim.lockstep`) обход идёт `updateBands`: всегда полосами (без потоков — главный проходит те же полосы по очереди), случайные числа у каждой полосы свои (сид кадра и столбец), отложенное — в порядке полос, общая фаза (ветер, тепло) — главным потоком. Так мир не зависит от числа потоков вкладки; сверяет `node tools/lockstep-check.js`. Новое состояние, которое пишут при обходе в своё поле объекта Sim (не в общий массив), у рабочих потоков — своё: в мультиплеере это расхождение.
- **Мультиплеер по сиду** (lockstep.js, net.js): шаг обязан зависеть только от мира и `Math.random`. Время (`performance.now`), порядок `Map` по чему-то внешнему, состояние рендера в шаге — расхождение вкладок (его поймает отпечаток, и вкладка будет перезапрашивать мир). Новое действие игрока, меняющее мир, — метод Sim в `MP_OPS` (net.js), иначе у вкладки его не будет. После правки — `node tools/lockstep-check.js`. Всё, что уходит по проводу (сообщения и мир целиком), — только то, что понимает `mpPack` (js/mp-wire.js): числа, строки, массивы, простые объекты, Map, Set, typed-массивы; функции пропадают, экземпляр класса становится простым объектом. Не опираться и на то, что сообщения ходят только между вкладками одного браузера: по сети нет ни общей памяти, ни Web Locks.
- Ветро-зависимые решения берут общий на кадр `_windRoll` и снимок `getWindVX/VY`, а не `Math.random()` на клетку: иначе цельные тела рвутся на части.
- Вероятности заданы «в кадр». Общая скорость времени — `sim.timeScale` в `main.js`, она меняет число вызовов `step()` за кадр. Внутрь механик её не встраивать.
- Сообщения коммитов на русском, короткой фразой о сути, как в `git log`.
